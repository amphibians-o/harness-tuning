# 構造と軽量化 — どんな構造にするか

Skills と Memory は**別の動作**。先に「どんな構造にするか」を決め、その形へ寄せる。SKILL.md の「4 軽量化」から読む。

## 目標の構造 — Skills

```
<skills-root>/
  <category>/
    DESCRIPTION.md      …「いつ読むか」を1行（索引の畳んだ行に載る手掛かり）
    WHEN_TO_USE.md      … そのカテゴリの一覧（SKILL.md の name＋description を自動生成）
    <name>/
      SKILL.md          … 索引に載るのは name と description だけ
      references/       … 詳細（索引に載らず、読んだときだけ載る）
      scripts/
```

- **索引に出るのは name と description だけ。** 説明には**見分ける語**（他のスキルと区別する語）を残す。
- **同名の解決順序**（同じ名前のスキルが複数の場所にあるとき）: 優先順位（例: プロジェクト > プロファイル > 作成先 > 外部）で1つに決まる。**同じ階層に同名が2つあると曖昧として拒否される**（推測しない）。内容が同一のコピーは浅い方が残る。
- 詳細は `references/` へ降ろす。本文を削っても索引コストは変わらない（載るのは name と description だけ）。
- カテゴリ名はパスの途中までで決まる（`<category>/<name>/SKILL.md` → `<category>`）。**同じ作業の続きを別スキルとして索引に立てると、名前が増える分だけ常時コストが増える。** 分割は独立に呼ばれる場面があるときだけ。

## 目標の構造 — Memory

```
<memory-home>/
  memories/
    MEMORY.md      … 毎ターン載る。常時効く規則と、判断に要る最小事実と、在処の1行
    USER.md        … 毎ターン載る
    details/*.md   … 詳細（原文のまま）。読んだときだけ載る
    index.md       … 在処の一覧（話題 → パス）。検索の入口（無ければ作る）
```

- ローダーは **`MEMORY.md` と `USER.md` の2ファイル名だけ**を読む（ディレクトリ走査なし）。だから詳細はどこへ移しても**読んだときだけ載る**。
- **常時効く規則は書き手が選べない場所**（SOUL か memory）に1箇所だけ置く。手順はスキルへ。
- **過去の memory を関連性で呼び出す**: 詳細を `details/` に置き、在処の一覧（`index.md`。無ければ作る）に1行を書く。呼び出しは **検索（語・症状・別名）→ 在処の行 → 読む**。経路行は**指す先が実在してから**書く。
- 詳細は**原文のまま**移す。要約すると正本が二つになる。
- 上限に当たったときの答えは「詳細をファイルへ移す」。**上限の値を動かす方向で解決しない。**

## 手順（Skills）

1. 触る前の重さを実送信の形で測る（スナップショットJSONは参考に留める）。
2. 説明の長いカテゴリは、索引のその行を**名前一覧へ降格**する（**名前は残る＝発見は壊れない**）。
3. 1本しかないカテゴリを親へ統合する（見出し行の分だけ減る。中身は不変）。
4. 説明を短くするときは**見分ける語を残し、周辺を削る**。語の途中で切らない（単語はトークンとして可読な状態で畳む）。
5. 一覧 `WHEN_TO_USE.md` を自動生成し、到達率を「畳む前／畳んだ後（索引だけ）／畳んだ後＋一覧を読む」で測る。索引だけで落ちても一覧で戻れば合格。
6. 一覧でも戻らないカテゴリだけ畳み込みを外す。

- 畳み込みの効果は、そのカテゴリ1つだけを外した／足した差で測る（他を全部畳んだ状態を固定する）。別々の実行から拾った数値を混ぜない。
- 効くのは**説明が長いカテゴリ**だけ。本数は効き目の代理指標にならない。

## 手順（Memory）

1. 面ごとの重さを測り、大きい項目から見る。
2. 詳細型の項目を、対応するスキル本文か `<memory-home>/details/*.md` へ**原文のまま**移す。
3. 移した先が実在するかを確かめてから、在処の1行に置き換える（壊れた経路を作らない）。
4. 常時効く規則は残す。短くするのはよいが消さない。
5. 置き換え後の重さを測り直す。**到達可能かどうか**（在処から実際に読めるか）を確かめる。

## スキルの重複を解消する

`description` の語の重なりで候補を出し、**両者の見出しと本文を読んで**3つに振り分ける。重なりは信号で、判定ではない。

| 判定 | 条件 | やること |
|---|---|---|
| 統合 | 扱う範囲が同じ（片方が他方の部分集合） | 扱う範囲の広い方を本体にし、薄い側を**原文のまま付録**として移し、同梱物（`references/`・`scripts/`）を移して退避する |
| 切り分け | 隣接するが別の仕事 | `description` に「何をするか」と「何は隣へ（→ 名前）」を**双方向で**書き、そのカテゴリの `WHEN_TO_USE.md` を再生成する |
| 別物 | 語彙が重なるだけ | 何もしない（同種ツールの別実装、別形式のファイル等） |

- **統合はトークンをほとんど減らさない**（名前が1本減るだけ）。目的は**選び間違いの防止**なので、削減量として報告しない。
- **統合済みの判定は見出しで行う。** スキル名の文字列で判定すると、別スキルへの参照行があるだけで「統合済み」と誤判定し、黙ってスキップする。
- 「本体に無い節」を見出しの**タイトル比較**で判断しない。書き方が違えば同じ内容でも別物に見える。**本文を読む。**
- 説明を書き換えたら、そのカテゴリの `WHEN_TO_USE.md` を再生成する（畳んだカテゴリでは説明が届く先は一覧だけ）。

## ツールの畳み込みと重複解消

**ツールのスキーマも毎リクエストに載る常時コスト**で、しばしば索引より重い。索引を畳んでもここが残る。

**畳み込み（遅延階層へ移す）**

- 遅延の仕組み（検索して見つけ、必要時に呼び出す入口）があるなら、**使う頻度の低いツールをそこへ移す**。移しても能力は失われず、名前と説明は一覧に残る。
- 実測は「**そのツールを使うセッションで、何回使うか**」で行う（使用セッション数だけでは決まらない。数え方を間違えると結論が反転する）。
  - 使うセッション内で何度も使うものは**即時のまま**（遅延化はセッションごとに往復を増やすので、常用では損）。
  - 稀にしか使わないものを移す（大多数のセッションでスキーマ分を節約できる）。
- **常時ある前提の道具は移さない。** 承認を求める道具・記憶を書く道具が代表。遅延化すると**使われなくなる**（上流の実測でも、遅延化した質問ツールの使用が大きく落ちたため既定から外してある）。迷ったら「その機能が使われなくなったときに困るか」で決める。
- **遅延化は無効化ではない。** 迷ったら「切る」ではなく「移す」を選ぶ。切ると名前ごと消えて再発見できない。
- 設定で戻せる形にする（本体更新で消えない種類の変更を選ぶ）。移すほど一覧が伸びるので、**差し引きで判断する**。

**重複解消**

- 同じ仕事をするツールが2つ以上あるときは、**片方を移すのではなく、片方を使わない**判断をする（重複は「選び間違い」を生む）。
- 見つけ方はスキルと同じ: 名前と説明の重なりで候補を出し、**実際の入出力と副作用を読んで**同じ仕事かを確かめる（名前や説明の一致は信号で、判定ではない）。
- 別の道具（プラグイン・外部サーバ）が同じ能力を出す場合も同じ扱い。**能力の重複は、常時コストと選択ミスの両方を増やす。**

## Memory と Skills の重なりを解消する

1. 同じ規則・同じ手順が SOUL／memory／スキルのどこに重複しているかを走査する。
2. 常時効く規則 → SOUL か memory の1箇所（毎ターン要るものを2ホップ先に置かない）。
3. 手順 → スキル。本文は読んだときだけ載る。
4. memory には在処の1行だけ残す。
5. 移した後、**原文の特徴語を移し先の全部から検索**して、落ちていないことを確かめる（検索対象を1つでも外すと偽の欠落が出る）。

## テキストを触るときの検証

- **テキスト置換はローダーの解釈と不整合になる。** 置換したらローダーのパーサで読み直し、frontmatter の型（リストが文字列化していないか）を確かめる。
- **索引の本数が変わったら理由を確認する**（編集ミスか、条件で隠れたか、カテゴリの再編か）。本数の増減は、起きた理由を言えるまで報告に使わない。

- **戻せる状態にしてから触る**のは前提（手順に数えない）。
- 到達率は代表タスクで前後比較し、実行間の揺れの範囲なら「発見は落ちていない」と判定する。
- 縮めた面は、削減量と**同じ重さ**で発見の変化を報告する。
